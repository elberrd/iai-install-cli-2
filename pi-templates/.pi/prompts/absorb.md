Read `.pi/skills/fia/SKILL.md`. This is the onboarding for an EXISTING project
(brownfield): the code is the source of truth — you read and document. NEVER
change code and NEVER create tasks here. After this command, the existing system
behaves like a project "with a PRD": /feature, /bug, /task and /goal work
on top of it.

Engineer's focus (optional): $@

Steps, in this order:

1. **Survey** — delegate to the `scout` (in parallel, if useful): stack and
   versions, folder structure, routes/screens, data model, integrations
   (auth, payments, storage), how to run it (scripts, `.env.example`, seeds) and
   how the tests are written.
2. **Map** — delegate to the `start-mapper` → `ai-docs/map.yaml`, including
   `commands.*` (dev/test/build) and test credentials (placeholder if none
   exist). Test users found in the code or the interview (seed scripts,
   `E2E_*` env vars, `+clerk_test` emails) also get one row each in the
   `ai-docs/test-credentials.md` roster (profile → email → where the
   password/code lives — env var names, never values).
3. **Artifacts** (you write these — they are orchestration documents):
   - `ai-docs/stack.md` — **stack manifest (source of truth)**: fill it in
     with what you OBSERVED in the code — one entry per layer (frontend,
     backend & API, database, ORM, auth, files, automations/jobs, publishing)
     with technology and version — the Automations layer records "none"
     explicitly when nothing runs outside the app (look for `automations/`,
     `jobs/`, `worker/` folders and `modal` references). An unidentified layer stays "decide later". If the installer
     left the manifest pending, replace the pending entries with the real stack.
     Also update the block between `<!-- stack-start -->` and `<!-- stack-end -->`
     in `AGENTS.md`. Then suggest `/stack` to generate the per-technology docs
     in `ai-docs/apis/` — it also runs the mandatory tooling research
     (docs/skills/CLI/MCP, ledger in `ai-docs/research/`) and equips the
     project from what it finds.
   - `ai-docs/PRD.md` — **as-built** PRD: what the system DOES today (actors,
     screens, flows, data model, integrations). Required header:
     "> Snapshot of the system on <date> — generated by /absorb. Edit freely;
     this document describes what EXISTS, not what is missing."
     If a human-written PRD.md already exists, do NOT overwrite it: write
     `ai-docs/PRD-as-built.md` and let me know.
   - `ai-docs/conventions.md` — observed house patterns (naming, folders,
     forms/state/styling libs, i18n, test format, error handling).
   - `ai-docs/components/registry.md` — AS-BUILT component registry: one
     row per reusable UI component the code already has (between the
     `registry:start/end` markers, status `installed`). It's the registry the
     task briefs will start requiring — suggest `/component sync` to maintain it.
   - **Project skill**: distill the conventions into short, actionable rules
     in `.pi/skills/project/SKILL.md` AND `.claude/skills/project/SKILL.md` —
     every future agent loads the house rules automatically.
4. **Short interview** (/grill style: ONE question at a time, always with a
   recommended answer, 5–8 total) ONLY about what the code doesn't reveal:
   product goal, what is untouchable, known debts, environment (dev database,
   seeds, test credentials), and one round of "what did I get wrong?"
   showing your summary. Record the answers back into the artifacts.
5. **Wrap-up** — list what was generated (paths) and the next commands:
   /kit (design-system audit — RECOMMEND it explicitly when the registry came
   out empty or the code shows duplicated/ad-hoc components) · /feature "what
   you want" · /bug "the symptom" · /task · /goal.
